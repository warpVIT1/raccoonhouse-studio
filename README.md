## Встановлення

1. Завантажте останній інсталятор зі сторінки
   [Releases](https://github.com/warpVIT1/raccoonhouse-studio/releases) —
   файл виду `RaccoonHouse Studio Setup <версія>.exe`.
2. Запустіть його. Установлення відбувається в теку користувача (не
   `Program Files`), тож права адміністратора не потрібні.
3. Готово — застосунок сам себе запускає після встановлення.

Оновлення далі відбуваються **самі**, без повторного завантаження
інсталятора вручну — див. [Автоматичне оновлення](#автоматичне-оновлення).

## Швидкий старт

Типовий шлях однієї серії через застосунок:

1. **Тайтли** — створіть тайтл (назву можна ввести вручну або знайти постер
   через Hikka — див. [Постери](#постери)). Кожен тайтл має статус —
   **Новий** → **В роботі** (перемикається сам, щойно десь у ньому зробили
   першу ізоляцію вокалу) → **Готово** (вручну, коли дубляж завершено). Клік
   на бейдж статусу дозволяє перемкнути його вручну в будь-яку сторону.
2. **Імпорт відео** — перетягніть файл (mp4, mkv, avi, mov, m2ts, ts) у
   вікно тайтлу. Номер сезону/серії можна виправити вручну. ffmpeg витягує
   лише лосслес-аудіодоріжку (FLAC) — відео не перекодовується.
3. **Ізоляція вокалу** — окрема кнопка в робочому вікні серії, див. нижче.
4. **Субтитри** — імпорт ASS/SRT прямо в робоче вікно; теги оформлення
   (Sign/Signs/OP/ED) розпізнаються окремо, перекриття рядків і помилки
   часових кодів підсвічуються.
5. **Маркери персонажів** — автовиявлення пауз/реплік (VAD) на вокальному
   стемі; кнопка-іконка поруч із назвою маркера підставляє код персонажа зі
   списку тайтлу одним кліком.
6. **Передача в Reaper** — експорт CSV-маркерів для імпорту тайм-лінії.
7. **Фінальний рендер** — готовий мікс із Reaper мультиплексується проти
   оригінального відео.

Усі довгі операції виконуються у фоні з наживо видимим відсотком (плитка
серії, робоче вікно, шапка вікна) і скасовуються кнопкою **✕** в будь-який
момент — скасування коректне, позначається як "Скасовано", а не помилка.

## Ізоляція вокалу та рендер

Кнопка "Ізоляція вокалу" в робочому вікні серії відкриває вибір методу —
ізоляція **ніколи не запускається автоматично**:

| Режим | Що робить |
|---|---|
| **MDX-Net / VR Arch / Demucs / MDX23C / BS-RoFormer** | Один конкретний метод і модель — найшвидший варіант |
| **★ Апекс** | Комбінований метод із подвійним проходом — див. [нижче](#апекс--комбінований-метод) |
| **Ensemble Mode** | Усереднює кілька обраних моделей в один результат |
| **Пакетний рендер** | Проганяє **кожну модель кожного методу** окремо (без усереднення), щоб порівняти на слух і обрати найкращу |

Пакетний рендер помітно довший за звичайну ізоляцію (з GPU все одно значно
швидше, ніж на CPU) і зберігає результати в
`<обрана тека>/<Тайтл>/<Метод>/<Тайтл>_S..E..(<Модель>).flac`. Після
завершення з'являється список усіх результатів з кнопкою "Обрати" навпроти
кожного — обраний файл стає інструменталом серії для фінального рендеру.

Якщо ввімкнено розподілену обробку потужності — поруч з'являється кнопка
"Запросити потужність", щоб виконати розділення на потужнішому ПК студії
(див. [Розподілена обробка потужності](#розподілена-обробка-потужності)).

**Фінальний рендер** мультиплексує готовий інструментал проти оригінального
відео (без перекодування відео) і окремо зберігає **той самий інструментал
у FLAC** поруч (`<файл>_dub.mp4` + `<файл>_dub.flac`) — зручна лосслес-копія
для архіву чи подальшої роботи в Reaper.

## Апекс — комбінований метод

**★ Апекс** — окремий, найагресивніший режим ізоляції: усереднює лінійку
топових моделей, тоді робить додатковий чистовий прохід, що ретельно
дочищає залишки вокалу, вирівнює гучність у місцях, де вокал забрав із
собою частину інструменталу, і додатково придушує ще почутий "витік" вокалу
за допомогою кореляційного аналізу. Мета — повністю прибрати вокал, а не
просто приглушити його.

- **Склад лінійки моделей редагується наживо** з Налаштувань (адмін-профіль)
  — додавання чи видалення моделі одразу підхоплюється **всіма** іншими
  інсталяціями студії через спільний Cloudflare Worker, без пересборки чи
  перезаливання застосунку.
- **Розмір сегмента й перекриття** для чистового проходу налаштовуються в
  "Розширених налаштуваннях" вікна ізоляції.
- Редагувати лінійку може лише адмін-профіль (див.
  [Профілі та адміністрування](#профілі-та-адміністрування)) — обирати й
  запускати Апекс може будь-хто.

## Власні моделі та GPU-прискорення

**Власні моделі (БЕТА)** — до стандартного списку кожного методу можна
додати будь-яку модель з реєстру
[`audio-separator`](https://pypi.org/project/audio-separator/) вручну, за
точною назвою файлу. Застосунок сам перевіряє, що модель реально розділяє
вокал/інструментал (а не, наприклад, прибирає луну чи шум), перш ніж
дозволити її додати.

**GPU-прискорення** — вимкнено за замовчуванням (опційно, в Налаштуваннях).
NVIDIA-відеокарта визначається автоматично; увімкнення завантажує один раз
~2.5 ГБ CUDA-бібліотек і прискорює всі методи розділення. На системах без
NVIDIA (AMD, вбудована графіка) розділення наразі йде на CPU.

## Розподілена обробка потужності

Ізоляція вокалу важка для CPU/GPU. Якщо один ПК студії слабкий, а інший
потужний, розподілена обробка дозволяє слабкому ПК попросити потужніший
виконати відокремлення вокалу, фінальний рендер чи ffmpeg-імпорт замість
себе — **повністю через інтернет, без жодного прямого з'єднання між двома
ПК** — з явною згодою реальної людини на іншому боці.

**Вимкнено за замовчуванням.** Доки перемикач у Налаштуваннях → "Розподілена
обробка потужності" вимкнено, ця функція взагалі нічого не робить.

### Усе через один Cloudflare Worker

Немає ні локальної мережі, ні проброса портів, ні VPN-мостів, ні ручного
введення чиєїсь IP-адреси — все, що потрібно двом ПК, це бути одночасно
підключеними (через `wss://`) до одного невеликого Cloudflare Worker'а (див.
`cloudflare-signaling/`, налаштовується в Налаштуваннях → "Пристрої онлайн";
типово вже вказано на спільний Worker студії):

1. **Хто зараз онлайн** — Worker веде живий список підключених ПК і
   розсилає його всім, щойно він змінюється.
2. **Згода** ("можна відокремити вокал на твоєму ПК?") — маленьке
   JSON-повідомлення, яке Worker пересилає від одного конкретного ПК до
   іншого через той самий WebSocket.
3. **Сам файл** (аудіо чи оригінальне відео вгору, готовий результат назад)
   — заливається у прив'язаний до Worker'а R2-бакет (`PUT /transfer/:id`),
   отримувач забирає його звідти (`GET /transfer/:id`), після чого обидві
   сторони видаляють об'єкт. Це навмисно "store-and-forward", а не пряма
   ретрансляція — у Worker'ів є ліміт часу/CPU на запит.

Розгортання власного Worker'а описано в `cloudflare-signaling/README.md`.

### Що означає "доступний"

ПК придатний для завдання, лише якщо на *ньому* розподілену обробку
увімкнено **і** хтось обрав активний профіль (аватар у сайдбарі). Друга
умова існує тому, що запит на згоду, який нікому показати, марний — якщо
профіль не активний, вхідні запити одразу відхиляються без спливаючого
вікна.

### Хід запиту

1. Якщо якийсь ПК уже погоджувався для **цього самого тайтлу** раніше — він
   використовується одразу, без повторного питання.
2. Інакше — усім доступним ПК одночасно надсилається запит на згоду.
3. На екрані кожного — спливаюче вікно (зі звуковим сигналом) з кнопками
   **Так / Ні** і 60-секундним відліком; без відповіді — автовідмова.
4. **Перший, хто погодився, перемагає** — решта запитів більше не
   очікується. Файли йдуть через R2-бакет Worker'а, робота виконується тим
   самим локальним пайплайном, результат повертається так, ніби обробка
   відбулася на власній машині.
5. Якщо ніхто не погодився — видно конкретну причину по кожному ПК
   (вимкнено / не залогінений / відхилив / тайм-аут / не з'єднався).

### Запам'ятована згода

Щойно ПК погодився для тайтлу — він використовується для *всіх наступних*
серій цього ж тайтлу без повторного питання. Інший тайтл — цикл
повторюється заново.

### Мережа й логи

Бекенд слухає лише на `127.0.0.1` — жоден інший ПК ніколи не підключається
до нього напряму, усе вихідне з'єднання йде як звичайний HTTPS/WSS-клієнт
до Worker'а. Кожна подія логується в `logs/power_share.log` (2 МБ × 3
резервні копії).

## Профілі та адміністрування

Аватар унизу сайдбару — справжня локальна ідентичність цього ПК (ім'я,
роль, колір), а не захардкоджене ім'я. Саме активний профіль означає
"залогінений" для розподіленої обробки.

Частина профілів може мати **адмін**-статус — надає доступ до:

- редагування лінійки моделей [Апекс](#апекс--комбінований-метод),
- вхідних [пропозицій і скарг](#зворотний-звязок-і-звіти),
- [звітів про розділення](#зворотний-звязок-і-звіти) з усієї студії,
- призначення адмін-статусу іншим профілям (перемикач `+admin`/`−admin`
  у вікні профілю).

Перший адмін в інсталяції студії розблоковується окремим прихованим шляхом
під час створення профілю — запитайте того, хто налаштовував вашу студію.
Це зручність для закритого кола довірених людей, а не справжній захист.

## Зворотний зв'язок і звіти

- **Пропозиції та скарги** — будь-хто може надіслати повідомлення прямо з
  Налаштувань; воно летить через той самий Cloudflare Worker, що й Power
  Share. Вхідний список бачать лише адмін-профілі.
- **Звіти про розділення** — кожен запуск ізоляції вокалу (локальний чи
  розподілений) автоматично формує звіт: тривалість, статус, помилки й
  тихі попередження, хто запускав, хто допоміг через Power Share. Адмін
  бачить час запуску у **своєму** часовому поясі з поясненням поясу
  користувача поруч. Кожен звіт додатково зберігається локально в теці
  проєкту (`data/reports/`) і клікабельний — розкриває всю інформацію в
  окремому вікні.

## Фоновий режим

Перемикач "Фоновий режим" у Налаштуваннях: коли увімкнено, закриття вікна
ховає застосунок у системний трей замість повного виходу — бекенд і Power
Share продовжують працювати у фоні (наприклад, щоб і далі допомагати іншим
ПК студії потужністю), поки ви не виберете "Вийти" з меню трея явно.

## Автоматичне оновлення

Застосунок перевіряє нові версії через **GitHub Releases** автоматично —
при старті й потім кожні 4 години (кнопка "Перевірити зараз" у
Налаштуваннях — для примусової перевірки). Завантаження починається лише
після натискання "Оновити" у вікні з описом змін.

Встановлення — **повністю тихе**: або "Перезапустити й встановити" одразу,
або тихе встановлення саме собою наступного разу, коли застосунок
закривають природним чином. Жодного вікна майстра встановлення.

**Стабільна версія і бета — два окремі канали.** Стабільний застосунок
оновлюється лише на стабільні релізи; бета-канал (версія з `-beta`) — лише
на новіші бета. Перехід зі стабільної на бету ніколи не пропонується як
автооновлення — лише необов'язковим сповіщенням "🧪 Доступна бета X.Y.Z".

Працює лише у зібраному застосунку — у `npm run dev` кнопка нічого не робить.

## Постери

Постер тайтлу шукається за назвою через публічний каталог
[Hikka](https://hikka.io) при додаванні/редагуванні тайтлу. Зображення **не
завантажуються на диск** — застосунок показує посилання на CDN Hikka
напряму (потребує інтернету; усе інше працює офлайн).

## Де зберігаються дані

Усе, що застосунок записує, лежить у теці `data/` **поруч із самим
інсталяційним файлом**, на тому ж диску, куди застосунок встановлено (не
завжди `C:`, як типовий `%APPDATA%`). При оновленні з версії, що зберігала
дані в `%APPDATA%`, вони переносяться автоматично один раз. У `npm run dev`
шлях лишається стандартним Electron-івським `userData`.

- `raccoonhouse.db` — SQLite (тайтли, серії, персонажі, дублери, субтитри,
  маркери, профілі, налаштування)
- `episodes/<id>/` — аудіодоріжка серії, вокальний стем (відео завжди
  показується з оригінального файлу)
- `models/` — завантажені ваги моделей audio-separator (кешуються)
- `reports/` — локальні копії звітів про розділення
- `logs/app.log`, `logs/power_share.log`, `logs/electron.log`

> **Обережно при ручному тестуванні збірки**: `release/win-unpacked/`
> генерується збіркою (`npm run build:exe` чи `electron-builder --dir`) і
> **повністю очищується** перед кожною новою збіркою — разом із будь-якою
> `data/`, що встигла туди потрапити. Ніколи не тримайте там реальні робочі
> дані студії; для звичайного користування — завжди через інсталятор.

## Для розробників

<details>
<summary><strong>Розгорнути — архітектура, розробка, збірка, публікація</strong></summary>

### Архітектура

- **Оболонка/UI**: Electron + React + TypeScript + Tailwind (`src/`, `electron/`)
- **Бекенд**: локальний FastAPI-сервер (`backend/`), запускається процесом
  Electron, зберігає дані в SQLite. Важкі ML-залежності (torch,
  audio-separator, scipy) імпортуються **лениво**, лише перед першим
  реальним використанням моделі — не при старті процесу, інакше кожен
  запуск застосунку чекав би десятки секунд ще до появи вікна.
- **Ізоляція вокалу**: [`audio-separator`](https://pypi.org/project/audio-separator/)
  (обгортка над моделями UVR — MDX-Net / VR Arch / Demucs / MDX23C / BS-RoFormer)
- **Сигналінг**: Cloudflare Worker + R2 (`cloudflare-signaling/`) — Power
  Share, зворотний зв'язок, звіти й синхронізація лінійки Апекс усі йдуть
  через нього, простими JSON-блобами з префіксом ключа
- **ffmpeg**: вбудований бінарник — лише витягування аудіо й фінальний
  мультиплексинг, жодного перекодування відео
- **Пакування**: electron-builder (NSIS) + PyInstaller (бекенд збирається в
  окремий `.exe`, Python на машині користувача не потрібен)

Electron запускає бекенд як дочірній процес при старті й **примусово
завершує все дерево процесів** (`taskkill /T /F`) при виході.

### Розробка

```
npm install
python -m venv .venv
.venv\Scripts\pip install -r backend\requirements.txt
npm run dev:full     # бекенд + Electron одночасно, в dev-режимі
```

> **ffmpeg**: `resources/bin/ffmpeg.exe` і `resources/bin/ffprobe.exe` **не**
> зберігаються в git (кожен ~240 МБ). Перед першою збіркою скопіюйте їх з
> будь-якого локального встановлення ffmpeg (`where ffmpeg`).

### Збірка інсталятора

```
npm run build:exe
```

PyInstaller (`backend-dist/raccoonhouse-backend.exe`) → рендерер (`dist/`)
+ Electron main/preload (`dist-electron/`) → electron-builder пакує все в
`release/win-unpacked/RaccoonHouse Studio.exe` і однофайловий інсталятор
`release/RaccoonHouse Studio Setup <версія>.exe`.

> **Windows Developer Mode**: NSIS-крок electron-builder створює символічні
> посилання під час розпакування архіву для підпису коду — потрібен
> Developer Mode (Параметри → Для розробників), лише під час *збірки*.

### Публікація нової версії

```
npm run publish
```

Потрібен `GH_TOKEN` (право `repo`) у змінних середовища. Збирає бекенд,
рендерер і інсталятор, завантажує в новий GitHub Release — **стабільний**
чи **бета**, залежно від `-beta` в номері версії з `package.json`. Обидва
канали автооновлення орієнтуються саме на цю позначку.
