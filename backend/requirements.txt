# audio-separator pulls its own compatible numpy/scipy/librosa/soundfile —
# do not pin those separately, it causes version conflicts (verified 2026-07-19).
#
# GPU acceleration, NVIDIA/CUDA only, via onnxruntime-gpu (used by the
# ONNX-based MDX-Net models) — on any other GPU vendor, no GPU at all, or a
# non-NVIDIA machine, this cleanly falls back to CPU with zero errors.
# torch itself is deliberately the plain CPU build, NOT +cu126: a full
# CUDA-enabled torch bundles its own ~3.9GB private copy of the CUDA runtime
# (cublas/cudnn/cufft/cusparse/etc in torch/lib), which pushed the packaged
# installer to ~3.2GB — GitHub Releases hard-rejects any single asset over
# 2GB ("size must be less than 2147483648"), and there's no other host set up
# for a file that size (verified 2026-07-19). Trade-off: the torch-based
# MDXC-family models run CPU-only (as they always did before GPU support was
# added); the onnxruntime-based MDX-Net models still get real CUDA
# acceleration via nvidia-cublas-cu12/nvidia-cudnn-cu12 below, which onnxruntime
# needs on its own now since there's no CUDA-enabled torch to borrow DLLs from.
# onnxruntime-gpu pinned to 1.20.1, deliberately NOT the latest (1.27.0) — it
# targets the CUDA 13 runtime, whose redistributable pip package
# (nvidia-cublas-cu13) is only a placeholder stub right now, so
# CUDAExecutionProvider silently fails to load. 1.20.1 targets CUDA 12.
# onnxruntime_providers_cuda.dll dynamically loads cudart64_12.dll,
# cublas64_12.dll, cudnn64_9.dll AND cufft64_11.dll — all four are required,
# not just cublas/cudnn: without nvidia-cuda-runtime-cu12/nvidia-cufft-cu12,
# CUDAExecutionProvider creation fails with "LoadLibrary error 126" and
# onnxruntime silently falls back to CPU (confirmed live 2026-07-19 — this
# is why GPU sat idle at 0% while CPU pegged at 80% despite
# ort.get_available_providers() listing CUDAExecutionProvider throughout;
# that check only reflects the onnxruntime build, not whether the DLLs
# actually load). separator_service.py's _add_nvidia_dll_dirs() puts these
# packages' bin/ dirs on PATH at runtime — required in addition to having
# them installed, since nothing else does this for a CPU-only torch.
# librosa's audio.py imports samplerate AND resampy as optional resampling
# backends, picked depending on the exact resample call — the VR Arch models
# (vr_separator) hit whichever one librosa happens to pick at runtime, and
# either can be needed depending on the input audio's actual sample rate
# (confirmed live 2026-07-25 twice: a synthetic 44.1kHz test clip only
# needed samplerate, a real episode's audio needed resampy instead — same
# "No module named ..." crash, different module). Both present by default in
# a fresh venv (pulled in transitively) but PyInstaller's static analysis
# doesn't see librosa's lazy/optional imports, so it silently drops them from
# the packaged build unless pinned here AND added as --hidden-import (see
# build-backend.py).
