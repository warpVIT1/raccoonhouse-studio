# RaccoonHouse Studio

Десктопний застосунок для студії дубляжу аніме на Windows: керування тайтлами й
серіями, ізоляція вокалу нейромережею, робота з субтитрами (ASS/SRT), передача
проєкту в Reaper, і опційна розподілена обробка між ПК студії — коли одному
комп'ютеру бракує потужності, можна попросити інший ПК студії зробити важку
роботу замість нього.

## Встановлення

1. Завантажте останній інсталятор зі сторінки
   [Releases](https://github.com/warpVIT1/raccoonhouse-studio/releases) —
   файл виду `RaccoonHouse Studio Setup <версія>.exe`.
2. Запустіть його. Установлення відбувається в теку користувача (не
   `Program Files`), тож права адміністратора не потрібні.
3. Готово — застосунок сам себе запускає після встановлення.

Оновлення далі відбуваються **самі**, без повторного завантаження
інсталятора вручну — див. [Автоматичне оновлення](#автоматичне-оновлення)
нижче.

## Як користуватись — крок за кроком

Типовий шлях однієї серії через застосунок:

1. **Тайтли** — створіть тайтл (назву можна ввести вручну або знайти постер
   через Hikka — див. [Постери](#постери) нижче). Тайтл видаляється кнопкою в
   його ж плитці (разом з усіма серіями). Кожен тайтл має статус — **Новий**
   (щойно створений, ще ніхто не працював), **В роботі** (десь у ньому вже
   зробили першу ізоляцію вокалу — застосунок сам перемикає цей статус,
   вручну нічого клацати не треба) чи **Готово** (позначається вручну, коли
   дубляж завершено). Клік на бейдж статусу в плитці тайтлу відкриває список,
   щоб перемкнути статус вручну в будь-який бік.
2. **Імпорт відео** — перетягніть відеофайл у вікно тайтлу (mp4, mkv, avi,
   mov, m2ts, ts — ffmpeg сам розбирає контейнер, окремої підтримки формату
   не треба). Номер сезону й серії можна виправити вручну перед імпортом
   (застосунок лише вгадує номер із назви файлу як стартову підказку). Далі
   ffmpeg витягує лише лосслес-аудіодоріжку (FLAC) — жодного перекодування
   відео. Якщо цей ПК слабкий, тут-таки можна попросити, щоб цей крок виконав
   потужніший ПК студії — див. [Розподілена обробка потужності](#розподілена-обробка-потужності).
3. **Ізоляція вокалу** — окрема кнопка в робочому вікні серії; див.
   [Ізоляція вокалу та рендер](#ізоляція-вокалу-та-рендер) нижче.
4. **Субтитри** — імпорт ASS/SRT прямо в робоче вікно серії; теги
   оформлення (Sign/Signs/OP/ED) розпізнаються окремо, перекриття рядків і
   помилки часових кодів підсвічуються.
5. **Маркери персонажів** — автоматичне виявлення пауз/реплік (VAD) на
   вокальному стемі, з прив'язкою до кодів персонажів для орієнтиру в Reaper.
   Замість того щоб щоразу вручну набирати код персонажа в назві маркера,
   кнопка-іконка поруч з полем назви відкриває список уже наявних персонажів
   тайтлу — код додається в назву одним кліком.
6. **Передача в Reaper** — експорт CSV-маркерів (і за потреби ReaScript) для
   імпорту тайм-лінії прямо в проєкт Reaper.
7. **Фінальний рендер** — після зведення дубляжу в Reaper, готовий мікс
   імпортується назад і мультиплексується проти оригінального відео; див.
   нижче.

Усі довгі операції (ffmpeg, нейромережа, детекція маркерів, віддалені
запити) виконуються у фоні з наживо видимим відсотком і статусом — у плитці
серії, в робочому вікні серії, і компактно в шапці вікна. Будь-яку з них
можна скасувати кнопкою **✕** прямо на індикаторі прогресу в будь-який
момент — скасування коректне (поточний крок доробляється, але результат не
застосовується), позначається як "Скасовано", а не як помилка.

## Ізоляція вокалу та рендер

Ізоляція вокалу нейромережею **не запускається автоматично** — це окрема дія
за натисканням кнопки "Ізоляція вокалу" в робочому вікні серії, де прямо в
цьому ж вікні обирається метод/модель:

- **MDX-Net / VR Arch / Demucs / MDX23C / BS-RoFormer** — один конкретний
  метод і модель, найшвидший варіант.
- **Ensemble Mode** — усереднює кілька моделей в один результат.
- **Пакетний рендер** — прогонятиме **кожну модель кожного методу**
  (не лише один дефолтний варіант на метод — весь список моделей, доступних
  у застосунку), кожна лишається окремим файлом (без усереднення), щоб
  можна було порівняти й обрати найкращу на слух. Це помітно довше за
  звичайну ізоляцію — з GPU все одно значно швидше, ніж на CPU. Перед
  запуском застосунок питає, в яку теку зберігати результати (нативний
  діалог вибору теки — скасування діалогу скасовує весь запуск). Файли
  лягають у структуру
  `<обрана тека>/<Тайтл>/<Метод>/<Тайтл>_S..E..(<Модель>).flac` — одна
  підтека на метод, усередині — файл на кожну модель цього методу. Після
  завершення з'являється віконце зі списком усіх результатів і кнопкою
  "Обрати" навпроти кожного — обраний файл стає інструменталом цієї серії
  для фінального рендеру; без цього кроку пакетний рендер сам по собі нічого
  не призначає.

Якщо ввімкнено розподілену обробку потужності — у вікні ізоляції вокалу
з'являється кнопка "Запросити потужність", щоб виконати розділення на
потужнішому ПК замість свого (див.
[Розподілена обробка потужності](#розподілена-обробка-потужності)).

**Фінальний рендер** ("Рендерити фінальну доріжку") мультиплексує вже
готовий інструментал серії проти оригінального відео (`ffmpeg`, відео
копіюється без перекодування) — і, окрім самого відео, окремо зберігає
**той самий інструментал у форматі FLAC** поруч, тим самим ім'ям
(`<файл>_dub.mp4` + `<файл>_dub.flac`) — відео завжди йде з перекодованою
під оригінальний кодек аудіодоріжкою, тож окремий лосслес FLAC-файл — єдина
бездоганна копія фінального аудіо, зручна для архіву чи подальшої роботи в
Reaper. Перед запуском так само питається тека збереження. Якщо ввімкнено
розподілену обробку потужності, поруч з'являється кнопка "Запросити
потужність" — надсилає відео та інструментал (стиснутий у FLAC для
передачі) на інший ПК і отримує назад готове відео з тим самим FLAC-файлом.

Прогрес відокремлення та рендеру видно наживо, а після завершення робоче
вікно й плитка серії оновлюються самі — не потрібно виходити з серії й
заходити знову.

> Якщо оновлюєтесь із версії, де ще генерувався 480p-проксі для перегляду:
> старі `proxy_480p.mp4`-файли нікуди не зникають самі — кнопка "Очистити" в
> Налаштуваннях → "Кеш прев'ю (480p)" прибирає їх з диска, нові серії такого
> кешу вже не створюють.

## Розподілена обробка потужності

Ізоляція вокалу важка для CPU/GPU. Якщо один ПК студії слабкий, а інший
потужний, розподілена обробка дозволяє слабкому ПК попросити потужніший
виконати відокремлення вокалу, фінальний рендер чи ffmpeg-імпорт замість
себе — **повністю через інтернет, без жодного прямого з'єднання між двома
ПК** — з явною згодою реальної людини на іншому боці.

**Вимкнено за замовчуванням.** Доки перемикач у Налаштуваннях → "Розподілена
обробка потужності" вимкнено, ця функція взагалі нічого не робить.

### Усе через один Cloudflare Worker

Немає ні локальної мережі, ні проброса портів, ні VPN-мостів, ні ручного
введення чиєїсь IP-адреси — все, що потрібно двом ПК, це бути одночасно
підключеними (через `wss://`) до одного невеликого Cloudflare Worker'а (див.
`cloudflare-signaling/`, налаштовується в Налаштуваннях → "Пристрої онлайн";
типово вже вказано на спільний Worker студії):

1. **Хто зараз онлайн** — Worker веде живий список підключених ПК і
   розсилає його всім, щойно він змінюється. Вкладка "Пристрої онлайн" в
   Налаштуваннях показує саме цей список.
2. **Згода** ("можна відокремити вокал на твоєму ПК?") — маленьке
   JSON-повідомлення, яке Worker пересилає від одного конкретного ПК до
   іншого через той самий WebSocket.
3. **Сам файл** (аудіо чи оригінальне відео вгору, готовий результат назад)
   — не йде через WebSocket і не йде напряму між ПК: відправник заливає
   файл у прив'язаний до Worker'а R2-бакет (`PUT /transfer/:id`), отримувач
   забирає його звідти (`GET /transfer/:id`), після чого обидві сторони
   видаляють об'єкт. Це навмисно "store-and-forward", а не пряма
   ретрансляція — Cloudflare Worker'и мають ліміт часу/CPU на один запит,
   що зробило б пряму ретрансляцію багатогігабайтного відео через сам
   Worker поганою ідеєю.

Розгортання власного Worker'а (якщо не використовуєте вже готовий) описано в
`cloudflare-signaling/README.md`.

### Що означає "доступний"

ПК вважається дійсно придатним для завдання, лише якщо на *ньому*:
1. Розподілену обробку увімкнено в Налаштуваннях, **і**
2. Хтось обрав активний профіль (аватар у сайдбарі — див.
   [Профілі користувачів](#профілі-користувачів)).

Друга умова існує тому, що запит на згоду, який нікому показати, марний: якщо
профіль не активний, вхідні запити одразу відхиляються як `"no_profile"`, без
жодного спливаючого вікна.

### Хід запиту

Є три точки входу — усі запускають той самий механізм узгодження, лише з
різним корисним навантаженням: ffmpeg-імпорт (у діалозі імпорту відео),
ізоляція вокалу (у вікні ізоляції) і фінальний рендер (кнопка поруч з
"Рендерити фінальну доріжку"). Спільний хід:

1. Бекенд дивиться на кожен ПК, знайдений через Worker. Якщо якийсь ПК уже
   погоджувався на запит для **цього самого тайтлу** раніше — він
   використовується одразу, без повторного питання (див. "Запам'ятована
   згода" нижче).
2. Інакше — усім доступним ПК одночасно (не по одному) надсилається запит
   на згоду через WebSocket-релей Worker'а — саме так реалізовано "всім,
   хто зараз доступний, приходить сповіщення", а не лише одному вибраному.
3. На екрані кожного такого ПК WebSocket показує спливаюче вікно внизу
   справа (з коротким звуковим сигналом, щоб запит не загубився, якщо вікно
   застосунку не в фокусі): хто просить, для чого саме, для якого
   тайтлу/серії, з кнопками **Так / Ні** і 60-секундним відліком. Якщо ніхто
   не натиснув за 60 секунд, цей ПК автоматично відмовляє (`"timeout"`) і
   просто не використовується.
4. **Перший ПК, що погодився, перемагає** — решта запитів більше не
   очікується. Відправник заливає файл(и) у R2-бакет Worker'а, погоджений
   пір забирає їх, виконує роботу локально (той самий пайплайн, що й при
   звичайній локальній обробці), заливає результат назад — відправник
   зберігає його так само, ніби робота відбулася на власній машині. Прогрес
   на екрані запитувача показує кожен етап окремо.
5. Якщо ніхто не погодився, запит завершується **конкретною причиною по
   кожному ПК** (вимкнено в налаштуваннях / ніхто не залогінений / відхилив /
   тайм-аут / не вдалося з'єднатися) — видно, що саме сталося і на якому ПК.

**Що саме передається**: невеликий JSON-запит на згоду через WebSocket і,
залежно від типу запиту — оригінальне відео, вже витягнута аудіодоріжка,
чи інструментал (у FLAC для рендеру), обидва напрямки через R2-бакет
Worker'а. Жодні дані SQLite чи інші файли проєкту не передаються.

### Запам'ятована згода (на рівні тайтлу, не запиту)

Щойно ПК погодився для конкретного тайтлу, цей самий ПК використовується для
*всіх наступних* серій *того самого* тайтлу без повторного питання — щоб не
спливало вікно на кожну з 24 серій сезону. Щойно робота переходить на
**інший тайтл**, весь цикл запитування повторюється заново.

### "Загальна потужність" — графік

Вкладка "Загальна потужність" у Налаштуваннях показує графік потужності
кожного знайденого ПК (VRAM відеокарти в ГБ) — свій ПК завжди виділений
кольором акценту студії, кожен інший має свій фіксований колір, пунктирна
лінія — середнє значення. Кольори перевірені на розрізнюваність для
дальтонізму.

### Мережева доступність

Бекенд слухає лише на `127.0.0.1` — жоден інший ПК ніколи не підключається
до нього напряму. Усе, що виходить назовні, робить це як звичайний вихідний
HTTPS/WSS-клієнт до Cloudflare Worker'а, тож локальний API не досяжний ні з
локальної мережі, ні з інтернету жодним чином.

### Логи

Кожен запит згоди/відповідь/таймаут і кожна віддалена обробка логуються в
`logs/power_share.log` (лише активність розподіленої обробки) та
`logs/app.log` (ті самі записи впереміш з рештою). Обидва — файли, що
ротуються (2 МБ × 3 резервні копії).

### "Позичаю потужність" — індикатор

Коли цей ПК виконує роботу **для чужого запиту**, зверху екрана — на
будь-якій вкладці — з'являється невелика панель "Допомагаю з потужністю:
<тайтл>, серія <N> для <нік>". Зникає сама, щойно обробка завершується.

## Автоматичне оновлення

Застосунок перевіряє нові версії через **GitHub Releases**
(`warpVIT1/raccoonhouse-studio`) за допомогою `electron-updater` —
автоматично: перевірка йде одразу при старті й потім кожні 4 години, поки
застосунок відкритий (кнопка "Перевірити зараз" у Налаштуваннях лишається
для примусової негайної перевірки). Якщо знайдено новішу версію,
з'являється вікно з описом змін — завантаження починається лише після
явного натискання "Оновити", нічого не тягнеться у фоні без відома.

Встановлення — **повністю тихе, без вікна інсталятора**: або людина сама
натискає "Перезапустити й встановити" (застосунок одразу закриється, тихо
встановиться і сам перевідкриється), або — якщо ніхто цього не зробив —
оновлення тихо встановлюється саме собою наступного разу, коли застосунок
закривають природним чином. Жодного разу не з'являється майстер
встановлення з кнопками "Далі". Встановлення в теку користувача (не
`Program Files`), тож тихе встановлення не вимагає прав адміністратора.

**Стабільна версія і бета — два окремі канали.** Стабільний застосунок
(версія без `-beta` в номері) автоматично оновлюється лише на новіші
стабільні релізи; окремий бета-канал (версія з `-beta`) — лише на новіші
бета. Якщо ви на стабільній версії й вийшла нова бета, це **не**
пропонується як звичайне оновлення (щоб не нав'язувати ще не обкатані
функції) — натомість унизу зліва з'являється маленьке, необов'язкове
сповіщення "🧪 Доступна бета X.Y.Z" з посиланням на сторінку релізу; можна
закрити й ніколи більше не побачити для цієї версії, або відкрити й
встановити вручну, якщо цікаво спробувати щось нове раніше.

Автооновлення працює лише у зібраному (упакованому) застосунку — у режимі
розробки (`npm run dev`) кнопка нічого не робить.

## Профілі користувачів

Аватар унизу сайдбару — це справжня локальна ідентичність цього ПК, а не
захардкоджене ім'я — натисніть, щоб створити/перемкнути/видалити локальний
профіль (ім'я, роль, колір). Саме це означає "залогінений" для розподіленої
обробки (див. вище). Зберігається в SQLite, окремо від списку `dubbers` (який
відстежує акторів озвучення, призначених на персонажів, а не хто керує
застосунком).

## Гарячі клавіші (робоче вікно серії)

Працюють, коли фокус не в текстовому полі (щоб не заважати звичайному
редагуванню):

- **Пробіл** — відтворити/пауза відео
- **← / →** — перемотка на 2 секунди назад/вперед
- **Shift + ← / Shift + →** — перемотка на 10 секунд назад/вперед

## Постери

Постер тайтлу можна знайти за назвою через публічний каталог
[Hikka](https://hikka.io) при додаванні/редагуванні тайтлу. Зображення **не
завантажуються на диск** — застосунок зберігає посилання на CDN Hikka напряму
й показує його наживо, тож постер потребує інтернету для показу (усе інше
працює повністю офлайн).

## Де зберігаються дані

Усе, що застосунок записує, лежить у теці `data/` **поруч із самим
інсталяційним файлом** — на тому ж диску, куди застосунок встановлено (не
завжди `C:`, як типовий Electron-івський `userData`, що завжди сидить у
`%APPDATA%` незалежно від місця встановлення). Модель дозволяє тримати важкі
дані (моделі нейромережі, GPU-рантайм, стеми серій — разом легко кілька ГБ)
подалі від системного диска, якщо застосунок встановлено на інший. При
оновленні з версії, що зберігала дані в `%APPDATA%`, дані **переносяться
автоматично** одноразово при першому запуску. У режимі розробки (`npm run
dev`) шлях лишається стандартним Electron-івським `userData`.

- `raccoonhouse.db` — SQLite (тайтли, серії, персонажі, дублери, субтитри,
  маркери, профілі, налаштування)
- `episodes/<id>/` — аудіодоріжка серії, вокальний стем (перегляд відео йде
  напряму з оригінального файлу, тут нічого не зберігається)
- `models/` — завантажені ваги моделей audio-separator (кешуються після
  першого разу)
- `logs/app.log`, `logs/power_share.log`, `logs/electron.log` — див.
  [Розподілена обробка потужності → Логи](#розподілена-обробка-потужності)

> **Обережно при ручному тестуванні збірки**: якщо запускати
> `release/win-unpacked/RaccoonHouse Studio.exe` напряму (без установлення),
> його `data/` теж лежатиме поруч, усередині `release/win-unpacked/` —
> наступна збірка (`npm run build:exe`) очищує цю теку повністю, разом із
> будь-якими реальними даними, що встигли туди потрапити. Для звичайного
> користування — завжди через інсталятор.

## Для розробників

### Архітектура

- **Оболонка/UI**: Electron + React + TypeScript + Tailwind (`src/`, `electron/`)
- **Бекенд**: локальний FastAPI-сервер (`backend/`), запускається процесом Electron,
  зберігає дані в SQLite
- **Ізоляція вокалу**: [`audio-separator`](https://pypi.org/project/audio-separator/)
  (обгортка над моделями UVR — MDX-Net / VR Arch / Demucs / MDX23C / BS-RoFormer)
- **ffmpeg**: вбудований бінарник — лише витягування аудіо при імпорті й
  фінальний мультиплексинг; жодного перекодування/стиснення відео ніде в
  застосунку немає — перегляд завжди йде з оригінального файлу
- **Пакування**: electron-builder (NSIS) + PyInstaller (Python-бекенд збирається
  в окремий `.exe`, тож користувачу не потрібен встановлений Python)

Electron запускає бекенд як дочірній процес при старті й **примусово завершує
все дерево процесів** (`taskkill /T /F` на Windows) при закритті вікна чи виході
із застосунку — бекенд не лишається висіти у фоні після закриття програми.

### Розробка

```
npm install
python -m venv .venv
.venv\Scripts\pip install -r backend\requirements.txt
npm run dev:full     # бекенд + Electron одночасно, в dev-режимі
```

> **ffmpeg**: `resources/bin/ffmpeg.exe` і `resources/bin/ffprobe.exe` **не** зберігаються
> в git (кожен ~240 МБ, більше за ліміт GitHub 100 МБ/файл). Перед першою збіркою
> скопіюйте їх туди з будь-якого локального встановлення ffmpeg — на dev-машині
> `where ffmpeg` покаже поточний шлях.

### Збірка інсталятора

```
npm run build:exe
```

Це запускає PyInstaller (бекенд → `backend-dist/raccoonhouse-backend.exe`), збирає
рендерер (`dist/`) та Electron main/preload (`dist-electron/`), потім пакує все
через electron-builder у `release/` — розпакований застосунок лежить у
`release/win-unpacked/RaccoonHouse Studio.exe`, а якщо крок пакування пройшов
успішно, поруч з'являється однофайловий інсталятор
`release/RaccoonHouse Studio Setup <версія>.exe`.

> **Windows Developer Mode**: крок electron-builder з NSIS створює символічні
> посилання під час розпакування допоміжного архіву для підпису коду. Windows
> блокує це для не-адміністративних процесів, якщо не увімкнено Developer Mode
> (Параметри → Конфіденційність і безпека → Для розробників). Це одноразове
> системне налаштування, потрібне лише під час *збірки* інсталятора, не під час
> роботи застосунку.

### Публікація нової версії

```
npm run publish
```

Потрібен токен `GH_TOKEN` з правом `repo` в змінних середовища. Це збирає
бекенд, рендерер і сам інсталятор, після чого завантажує їх у новий GitHub
Release — **стабільний** (без `-beta` в номері версії з `package.json`) чи
**бета** (з `-beta`), залежно від того, яку версію проставлено перед
публікацією; позначка "Pre-release" на GitHub виставляється відповідно.
Обидва канали автооновлення (див.
[Автоматичне оновлення](#автоматичне-оновлення) вище) орієнтуються саме на
наявність/відсутність `-beta` в номері версії — окремого перемикача каналу
десь іще немає.
